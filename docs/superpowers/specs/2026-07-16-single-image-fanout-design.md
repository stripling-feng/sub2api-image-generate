# 图片生成单张请求拆分设计

## 目标

- 所有图片模型允许用户选择 1–10 张。
- 每次上游请求固定发送 `n=1`。
- 用户选择多张时，后端在同一 `requestId` 下创建多个独立任务。
- 每个任务独立计费、轮询、成功或失败，不影响同批次其他任务。

## 数据与配置

新增 V5 数据库迁移，将四个图片模型的 `max_count` 统一更新为 10。后台不重新开放最大张数配置，工作台继续从 `/api/images/models` 获取数量上限。

不新增批次表。现有 `generation_jobs` 已包含 `request_id`、`request_index` 和 `request_total`，可以直接表达一个批次中的多个子任务。

## 生成流程

收到数量为 `count` 的请求后：

1. 生成一个批次 `requestId`。
2. 循环创建 `count` 个 `GenerationJob`，每个任务的 `count` 固定为 1。
3. 每个任务记录同一个 `requestId`，并设置独立的 `request_index` 和共同的 `request_total`。
4. 每个任务按一张图片的模型单价独立冻结余额。
5. 每次调用上游都固定传 `n=1`。
6. 上游创建失败时，只释放或结算当前任务的冻结金额并把该任务标记为失败；循环继续处理其他任务。
7. 接口返回原批次 `requestId` 和用户请求的总张数。

## 轮询与计费

每个上游任务拥有独立的任务 ID和账单状态，继续复用现有轮询器：

- 成功：保存当前图片并结算一张的费用。
- 失败或超时：释放当前任务冻结的一张费用。
- 开启失败计费时：当前失败任务按既有规则结算一张费用。

批次总费用自然等于所有成功计费子任务金额之和，不新增批次账单协调器或分布式事务。

## 前端行为

工作台所有模型的数量输入范围统一为 1–10。提交协议不变，仍发送一次请求和所选 `count`；前端不循环调用生成接口。

历史和结果页面继续按 `requestId` 聚合同批次任务，因此一次选择 4 张仍表现为一个生成批次。

## 错误处理

- 单个子任务创建失败不会中断其他子任务。
- 每个失败任务保存明确错误和账单状态。
- API Key、余额或配额不足导致的任务失败按当前计费服务返回错误记录。
- 输入数量小于 1 或大于 10 时返回 422。

## 验证

- 验证数量 4 会创建 4 个任务，且所有上游请求均为 `n=1`。
- 验证四个任务共享 `requestId`，索引为 1–4，总数均为 4。
- 验证每个任务冻结单张价格，批次总额为单价乘以数量。
- 验证其中一个上游请求失败时，其他请求仍被创建和轮询。
- 验证 V5 后四个模型的公开配置均返回 `maxCount=10`。
- 运行完整后端测试和工作台生产构建。
